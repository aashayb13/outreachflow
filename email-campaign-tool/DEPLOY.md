# Deploying email-campaign-tool to Render

This guide takes you from a local clone to a live deployment on Render with a
persistent database, encrypted secrets, and the API Integrations tab live.

---

## What gets deployed

- **1 Render web service** — Node.js, runs `node src/server.js`
- **1 persistent disk** (1 GB) mounted at `/data` for the SQLite database
- **Auto-deploy on push to `main`**
- **Health check** at `/health` (queries the DB so failures are real)

The repo layout is a monorepo:

```
outbound-flow-marcus/         ← repo root
├── render.yaml               ← canonical Blueprint (Render reads this)
├── email-campaign-tool/      ← the app
│   ├── render.yaml           ← copy for manual / non-Blueprint deploys
│   ├── src/
│   ├── views/
│   └── package.json
└── n8n-workflows/, etc.
```

The Blueprint at the **repo root** uses `rootDir: email-campaign-tool` to
point Render at the subdirectory.

---

## Prerequisites

1. A GitHub repository containing this codebase (private is fine).
2. A Render account: https://dashboard.render.com
3. (Optional, recommended) SMTP credentials — Gmail App Password, Mailgun, or
   SendGrid. You can deploy without these and add them later.

---

## Step 1 — Push the code to GitHub

```bash
git add .
git commit -m "Render deployment ready"
git push origin main
```

Make sure `render.yaml` exists at the repo root and `email-campaign-tool/` is
committed. The `.gitignore` correctly excludes `data/`, `logs/`, `node_modules/`,
and `.env` — these should NEVER be committed.

---

## Step 2 — Connect the repo to Render (Blueprint mode)

1. In the Render dashboard, click **New +** → **Blueprint**.
2. Connect your GitHub account if you haven't already, and select this repo.
3. Render will detect `render.yaml` and show a preview of the resources it
   will create:
   - Web service: `email-campaign-tool` (Starter plan, $7/mo)
   - Disk: `email-campaign-data` (1 GB at `/data`)
4. Click **Apply**.

Render will start the first build but it will **fail or stay in "needs input"
state** until you set the environment variables that are marked `sync: false`
in the Blueprint. That is the next step.

---

## Step 3 — Set environment variables

In the Render dashboard, go to your service → **Environment** tab and fill in
the variables marked with ⚠️ below. Variables not marked are pre-filled by
the Blueprint.

### Required (you must set these)

| Variable | Notes |
|---|---|
| **`APP_SECRET`** ⚠️ | **This is your dashboard login password.** Use a long random string (e.g. `openssl rand -hex 32`). Save it somewhere safe — it cannot be recovered, only rotated. Also used to sign JWTs and to encrypt integration credentials. |
| **`BASE_URL`** ⚠️ | The public URL of your service. After first deploy, Render assigns one like `https://email-campaign-tool-abcd.onrender.com`. Set this and redeploy. Or set it to your custom domain. |
| **`TRACKING_DOMAIN`** ⚠️ | Public URL used in open/click tracking pixels. Usually the same as `BASE_URL` unless you have a separate tracking subdomain. |

### SMTP (required to send email — can be added later)

| Variable | Example |
|---|---|
| `SMTP_HOST` | `smtp.gmail.com` |
| `SMTP_PORT` | `587` (default in Blueprint) |
| `SMTP_SECURE` | `false` (default in Blueprint) |
| `SMTP_USER` | Your Gmail / Mailgun / SendGrid username |
| `SMTP_PASS` | App Password or API key |
| `SMTP_FROM_NAME` | `"Patriot Tech Systems"` |
| `SMTP_FROM_EMAIL` | `you@yourdomain.com` |

> **Gmail tip:** you cannot use your normal password. Generate an App Password
> at https://myaccount.google.com/apppasswords (2FA must be enabled).

### Optional

| Variable | Default | Notes |
|---|---|---|
| `API_KEY` | empty | Master key for `X-API-Key` header on `/api/*`. Generate with `openssl rand -hex 32`. Useful for n8n / external automation. |
| `WEBHOOK_SECRET` | auto-generated | Used to sign outbound webhook payloads. Already auto-generated by the Blueprint. |
| `SEND_RATE_PER_SECOND` | `5` | Outbound email throughput cap. |
| `SEND_RATE_PER_DAY` | `2000` | Daily send cap (Gmail = 500/day for free, 2000 for Workspace). |
| `RATE_LIMIT_WINDOW_MS` | `900000` | API rate-limit window (15 min). |
| `RATE_LIMIT_MAX_REQUESTS` | `100` | Max requests per IP per window. |
| `NODE_ENV` | `production` | Already set by Blueprint. Don't change. |
| `PORT` | `10000` | Already set by Blueprint. Don't change. |
| `DB_PATH` | `/data/campaigns.db` | Already set by Blueprint. The `/data` mount is the persistent disk. |

---

## Step 4 — First deploy

After setting `APP_SECRET`, click **Manual Deploy → Deploy latest commit**.

Watch the logs. You should see:

```
Database loaded from: /data/campaigns.db   (or "New database created" on first boot)
Database schema initialized
Email Campaign Tool — Running!
Environment: production
Scheduler started (campaign check: 1min, sequences: 2min, stats: hourly)
```

Then the health check at `/health` will turn green and Render will mark the
service **Live**.

---

## Step 5 — First login

1. Open your service URL (e.g. `https://email-campaign-tool-abcd.onrender.com`).
2. You'll be redirected to `/login`.
3. Enter your `APP_SECRET` value as the password.
4. You're in.

---

## Step 6 — Configure integrations (optional)

1. Go to the **API Integrations** tab in the sidebar.
2. Pick a provider (Apollo, Hunter, Lead Magic, Clearbit, Snov.io).
3. Paste your provider API key. It's encrypted with AES-256-GCM at rest.
4. Click **Test** to verify the credentials.
5. Click **Search**, fill in criteria, and **Preview (Dry Run)** before importing.

---

## Step 7 — Set BASE_URL and TRACKING_DOMAIN (post-deploy)

After your first deploy, Render assigns a `*.onrender.com` URL. Go back to the
**Environment** tab and set:

- `BASE_URL=https://your-service.onrender.com`
- `TRACKING_DOMAIN=https://your-service.onrender.com`

Save → Render auto-redeploys. This is needed so unsubscribe links and tracking
pixels point at the right host.

---

## Custom domain (optional)

1. Render service → **Settings** → **Custom Domains** → **Add Custom Domain**.
2. Add the CNAME record at your DNS provider as instructed.
3. Render auto-provisions a Let's Encrypt cert.
4. Update `BASE_URL` and `TRACKING_DOMAIN` to the custom domain and redeploy.

## Operations

### Logs
- Render dashboard → service → **Logs** tab. Logs are JSON in production
  (`{"level":"info","message":"..."}`) so they're easy to filter and ingest.
- Local dev still gets human-readable colorized console output.

### Database backups
The Render starter plan does NOT include automated disk snapshots. Two options:

1. **Manual download**: SSH into the service (Render → Shell) and copy
   `/data/campaigns.db` somewhere safe periodically. Or use the contacts
   export endpoint:
   `curl -H "X-API-Key: $API_KEY" https://your-service.onrender.com/api/contacts/export/csv -o backup.csv`
2. **Upgrade to a plan with disk snapshots** for automatic backups.

### Restarting the service
Render dashboard → service → **Manual Deploy → Clear build cache & deploy**.

### Rotating APP_SECRET
**Be careful** — rotating `APP_SECRET` will:
- Invalidate all existing JWTs (everyone has to log in again)
- Make existing **integration credentials un-decryptable** (you'll need to
  re-enter API keys for each integration)

If you rotate it, plan to re-enter all integration credentials immediately.

### Scaling
This app uses sql.js with file persistence — it's **single-instance only**.
Do NOT scale to multiple instances on Render; the in-memory database state
will diverge across instances. Vertical scaling (bigger plan) is fine.

## Troubleshooting

### "Cannot GET /integrations" → 404
You're hitting an old running process. Restart the service from the Render
dashboard (Manual Deploy → Deploy latest commit).

### Login says "Invalid password"
You're entering the wrong `APP_SECRET`. Reset it in the Environment tab and
redeploy. Remember: rotating it will require re-entering all integration API
keys.

### Health check failing
1. Check logs — usually a missing env var or a DB write error.
2. Verify the disk is mounted: SSH into the service (`Shell` tab) and
   `ls -la /data`. You should see `campaigns.db`.

### "EROFS: read-only file system" errors
Something is trying to write outside `/data`. The logger writes to stdout in
production so this should not happen, but if it does, look for a code path
that writes to `./logs` or `./data` in production.

### Render auto-deploy not triggering
Check **Settings → Build & Deploy → Auto-Deploy** is enabled. The Blueprint
sets this to `true` by default.

### Cookies won't set / "Secure cookie over insecure connection"
This means `trust proxy` isn't being honored. The fix is already in
`server.js` (`app.set('trust proxy', 1)`). If you see this error after
deploying, you're probably running an old build — redeploy.

## Production hardening checklist

These are all already in place — listed here so you can verify:

- [x] `trust proxy` set in Express (for secure cookies + real client IPs)
- [x] Helmet enabled (CSP off because we use inline scripts in EJS)
- [x] CORS enabled
- [x] Compression enabled
- [x] API rate limiting (`express-rate-limit`) on `/api/*`
- [x] Tighter rate limit (30/min) on integration `/test`, `/search`, `/import`
- [x] Cookie `secure: true` in production (HTTPS only)
- [x] Cookie `httpOnly: true` (no JS access)
- [x] JWT auth + API key auth both supported
- [x] Permission gates (`read` / `write` / `admin`) on mutating routes
- [x] Integration credentials encrypted at rest (AES-256-GCM)
- [x] Suppression-list-aware contact import
- [x] Audit log for every integration test/search/import
- [x] Database auto-save every 30s + on every transaction commit
- [x] Graceful shutdown (SIGTERM/SIGINT) — saves DB, closes connections
- [x] Health check queries the DB so it catches DB failures
- [x] Production logging to stdout (JSON) for Render's log aggregator
- [x] No secrets in committed files (`.env` is gitignored)
